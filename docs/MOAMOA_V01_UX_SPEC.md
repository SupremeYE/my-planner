## 2. 디자인 제안: Cozy Life Diary + Tiny RPG

“나의 하루, 시간, 목표, 습관, 경험을 하나씩 모아가며 성장하는 귀여운 라이프 아지트.”

기록량이나 성과보다 **다시 들어오기 편한 공간**을 우선한다. 앱을 열면 이번 주의 방향을 먼저 보고,
한 가지를 체크하거나 짧게 기록한 뒤 나갈 수 있어야 한다. 모든 기능을 홈에 나열하지 않는다.

| 기록 | 지금 남길 것을 고르고 나를 이해 | 즐겨 기록 4개 → 시간 분석 → 생활 기록/회고 | 처음부터 모든 건강 기능 나열 |
| 나의 정원 | 성장과 장기 방향을 돌아보기 | 캐릭터·성장, 월간·연간 목표, 씨앗/버킷리스트, 하이라이트 | 꾸미기 상점·재화·랭킹 |

모바일은 하단 5개 메뉴, PC는 왼쪽 5개 메뉴를 사용한다. **빠른 기록은 메뉴가 아니라 전역 동작**이다.
모바일 오른쪽 아래의 작은 기록 버튼, PC 상단 버튼과 화면 안 추가 진입점이 같은 시트를 연다.
기존 서비스의 메뉴/홈은 그대로 두었다.

기록 내부 분류는 시간 / 건강(수면·운동·컨디션·생리·셀프케어) / 마음(감정·일기) / 회고로 묶는다.
처음에는 시간·마음·수면·하루 한 줄만 바로 보이고 나머지는 펼쳐서 찾는다. 실제 사용 빈도로
즐겨 기록 순서를 조정하는 것은 후속 검토이며 이번 시안에서 설정 기능을 만들지는 않았다.

## 4. 화면별 설계

### 오늘 — 모바일 우선

1. 날짜·짧은 인사와 작은 캐릭터. 성장 상태는 작은 보조 표시다.
2. 실제 활동 시간과 데일리 회고 진입을 한 줄 요약으로 제공한다.
3. **이번 주 목표**를 첫 화면 안에 표시한다. 두 목표의 개별 진행률과 전체 가중 진행률을 구별한다.
4. 오늘의 핵심 TODO는 기존 `isTop3` 기준 최대 3개다. 추가한 일반 TODO는 할 일의 전체 목록에서 확인한다.
5. 아래에는 오늘의 약속 요약, 카테고리별 실제 시간, 조금 더 넓은 회고 진입을 배치한다.
6. 기록 버튼은 스크롤 중에도 접근 가능하다. 홈에서 목표 편집이나 모든 로그 입력을 요구하지 않는다.

390×844 렌더에서 주간 목표는 스크롤 없이 보인다. “홈 진입 10초 안에 목표 확인”은 설계 목표다.
실제 사용자 대상 시간 측정을 완료한 것은 아니다. 아래 카드는 자연스러운 세로 스크롤로 확인한다.

PC는 인사/목표/핵심 TODO를 왼쪽, 캐릭터/일정을 오른쪽에 배치한다. 캐릭터가 업무 정보를 가리지 않으며
카테고리 시간과 회고를 아래에서 이어서 본다. 화면 폭이 달라도 데이터와 완료 기준은 같다.

### 캘린더 — 같은 자료의 다른 보기

**주간 일정**은 PC에서 월~일 7열과 PLAN/DO 두 레인을 사용한다. 계획은 옅은 카테고리색,
실제는 세이지 레인으로 구별한다. 일정을 누르면 전체 제목과 날짜·시간을 편집하는 시트가 열린다.
좁은 시간 블록은 제목을 축약하고 툴팁/접근 가능한 전체 이름을 제공한다. 축약은 데이터 잘림이 아니다.

모바일은 7열을 억지로 축소하지 않고 요일 선택 후 하루의 PLAN/DO를 본다. 계획을 옮겨도 실제 시간
블록은 이동하지 않는다. 이 시안은 **클릭 후 날짜/시간 변경**을 구현했으며 드래그/리사이즈는 구현하지 않았다.
실제 적용 시 기존 Timeline과 WeekAllDayLane의 이동 동작을 먼저 재사용한다.

실제 기록이 있는 기존 Event에는 별도 실행일이 없다. 날짜 변경으로 실제 기록까지 이동하는 것처럼
시연하지 않기 위해 해당 일정의 날짜 이동을 제한했다. 실제 기록 없는 일정과 TODO 계획은 날짜 이동을
시연할 수 있다. 필요한 모델 확장은 7절에 정리했다.

**주간 플래너**는 PC에서 목표/날짜 미정/시간 요약을 왼쪽에, 월~일 노트 카드를 오른쪽에 둔다.
빈 여덟 번째 칸은 “모든 칸을 채우지 않아도 괜찮다”는 여백으로 사용한다. 아래에는 전체 TODO 펼침,
습관 트래커, 주간 회고가 이어진다.

모바일은 상단 조작부를 압축하고 목표 → 요일 선택 → 선택일 계획 → 날짜 미정 → 습관 → 시간/회고로
이어진다. 7일 카드를 모두 길게 쌓지 않는다. “이번 주 전체 할 일”을 펼치면 주간 전체 자료를 본다.
습관은 모바일에서 이름 아래 7개의 넓은 체크 칸을 두어 최소 약 44×44px의 터치 영역을 확보했다.
미래 날짜 체크는 비활성화하며 미기록은 빈칸으로 표현한다.

**월간/일간**은 탐색 구조와 기본 레이아웃을 제시한다. 모바일 월간은 아주 작은 제목 대신 항목 수를
표시하고 날짜를 눌러 일간 전체 내용을 확인한다. 고급 반복 편집·겹침 배치·확장 시간축은 상세 시안에서 제외했다.

### 할 일

- 오늘 / 이번 주 / 날짜 미정과 카테고리 필터를 조합한다.
- 하나의 TODO ID를 여러 화면에서 표시한다. 전용 Quest 테이블을 만들지 않는다.
- 연결 목표 진행률은 STEP 2 공통 계산을 사용한다. 완료 체크는 확인 후 표시한다.
- 수동 완료와 연결 TODO 계산, 취소·백로그·날짜 미정의 기준을 바꾸지 않는다.
- 완료 축하는 작은 문구로 충분하며 자동 화면 이동·큰 팝업·XP 차감을 하지 않는다.

### 기록과 빠른 기록

빠른 기록은 기본 **할 일** 탭이다. 제목만 필수이며 날짜는 오늘/미정/다른 날짜, 카테고리와 목표 연결은
필요할 때 펼친다. 날짜를 선택한 요일 카드에서 추가하면 그 날짜를 미리 채운다. 날짜 미정 카드에서는
날짜를 비워둔다.

**시간** 탭은 연결할 TODO(활동명) → 소요 시간(15/30/60분 또는 직접 입력) → 날짜 순이다.
대표 카테고리는 TODO의 태그를 보여주며 멋대로 태그를 교체하지 않는다. 기존 복수 추적 태그의 시간 분할은
계산 엔진에 그대로 맡긴다. 메모 칸은 시안이며 기존 시간 블록에 메모 컬럼이 있는 것처럼 가정하지 않는다.

시간 시트의 반영 버튼은 필드 스크롤과 분리해 항상 보인다. 날짜/메모/다른 옵션은 필요한 경우에만
스크롤한다. 익숙해진 사용자가 10초 이내 기록하는 것을 목표로 하되 이번 단계에서 인간 사용성 측정을
수행한 것은 아니다.

**독립 활동**은 `후속 설계`로 표시하고 반영 버튼을 비활성화했다. TODO 없이 실제 저장되는 기능처럼
보이게 하지 않는다. 활동 기록을 만들기 위해 숨겨진 가짜 TODO를 생성하지도 않는다.

시간 분석은 일간/주간/월간을 전환하며 같은 `aggregateActivity`를 사용한다. 계획은 실제 시간에
합산하지 않는다. 수면·운동 등의 생활 로그를 활동 시간에 자동으로 다시 더하지 않는다.

수면·마음·일/주/월 회고는 짧은 입력과 메모리 반영만 시연한다. 다른 생활 기록은 분류와 탐색 위치만 제안한다.

### 나의 정원

캐릭터 한 명과 성장 단계 표시, 월간/연간 방향, 버킷리스트/씨앗, 작은 성취를 배치한다. 초기 시안의
레벨·XP 수치는 고정 예시이며 TODO 체크로 실서비스 XP를 바꾸지 않는다. `Lv.2`, 140/800은 기존
레벨 곡선에서 총 XP 940인 경우의 예시다.

기존 ProfileView는 완료 수·습관·현재 streak 등에서 XP를 계산한다. 현재 streak 보너스가 바뀌면 총 XP도
변할 수 있으므로, “쉬어도 경험치가 내려가지 않는다”는 새 약속을 실제로 보장하려면 XP 정책의 별도
검토가 필요하다. 이번 단계에서는 기존 XP 코드나 데이터 모델을 변경하지 않았다.

## 5. 주요 사용자 흐름과 저장 상태

| 흐름 | 시연 동작 | 실제 구현 시 연결 |
| --- | --- | --- |
| 하루 시작 | 오늘 → 상단 목표 확인 → 핵심 TODO 체크 → 짧은 축하 | 같은 TODO ID, `updateTodo`, `weeklyRollup` |
| 빠른 할 일 | 기록 버튼 → 제목 → 모아두기 | `addTodo`의 안정적인 생성 ID와 확인 결과 |
| 시간 기록 | 시간 탭 → 연결 TODO → 분 단위 소요 → 모아두기 | 기존 `todo_time_blocks`, 공통 시간 집계 |
| 한 주 정리 | 캘린더 → 주간 플래너 → 요일/날짜 미정 → 습관 → 회고 | 기존 TODO/Event/Habit/WeeklyReview |
| 계획 이동 | 시간표/할 일의 편집 → 날짜·시각 → 확인 | 기존 날짜 이동 헬퍼와 확인 저장 액션 |
| 하루 마무리 | 홈 회고 → 한 문장 → 작은 기록 | 기존 데일리 회고 필드 |
| 실패 복구 | 시안 옵션의 다음 반영 실패 → 입력 유지 → 재시도 → 완료 | STEP 2의 요청 상태·동일 ID·동일 payload |

프로토타입 반영은 약 450ms 지연한 **메모리 시연**이다. 성공 전에는 이전 값/초안을 유지한다.
실패를 성공처럼 체크하지 않으며 재시도는 동일 ID를 사용한다. 시트 안 알림은 모달의 접근성·포커스
범위 안에 두었다. 실패 후 재시도 성공 시에는 완료/닫기를 표시한다.

운영 제품의 오프라인 저장이나 새로운 저장 보장을 구현한 것이 아니다. 새로고침/샘플 초기화는 이 시안의
메모리만 지운다. 브라우저 localStorage/sessionStorage나 사용자 인증 정보를 초기화하지 않는다.

## 7. 데이터 모델 검토 — 변경 실행 없음

### 현재 모델로 가능한 것

- 월간 목표 → 주간 목표는 `monthlyGoalId`, 주간 목표 → TODO는 `weeklyGoalId`를 유지한다.
- 오늘/플래너/할 일은 같은 Todo 행을 조회하고 같은 완료 상태를 표시한다.
- TODO에 연결한 소요는 기존 `todo_time_blocks`의 `todoId`, `date`, `elapsedSec`를 사용한다.
  시각 없는 소요도 분석에 포함되지만 시간표 위치를 임의로 만들어 그리지 않는다.
- 주간 목표에 연결된 날짜 미정 TODO는 목표의 `weekKey`로 주간 목록에 포함할 수 있다.
- 습관은 기존 체크 날짜를 요일별로 펼친다. 새 체크 테이블을 화면별로 만들지 않는다.

### 특정 주에만 배정된 날짜 미정 TODO

현재 Todo에는 독립 `weekKey`가 없다. `BrainstormItem.weekKey`는 아이디어용이며 TODO의 주차 필드로
대신 쓰면 의미가 달라진다. 주간 목표 연결을 억지로 만들거나 가짜 날짜를 넣는 것도 권장하지 않는다.

MVP 확장 후보는 nullable `Todo.plannedWeekKey` / DB `planned_week_key` 한 필드다. **이름·스키마·SQL은
확정하지 않았고 구현하지 않았다.** 추천 읽기 규칙은 다음과 같다.

1. 날짜가 있으면 해당 날짜의 주간 일정/플래너에 배치한다.
2. 날짜가 없고 명시적 plannedWeekKey가 있으면 그 주의 날짜 미정 영역에 배치한다.
3. 둘 다 없으면 기존 연결 주간 목표의 weekKey로 보완한다.
4. 어떤 주에도 속하지 않으면 전역 날짜 미정 목록에 남긴다.

목표 진행률은 배치 주간으로 TODO를 다시 거르지 않고 STEP 2 연결 관계를 따른다. 날짜 지정/해제 시
명시적 주차를 보존할지 갱신할지는 UX 결정 후 정의해야 한다. 기존 데이터 일괄 보정은 하지 않는다.
다중 주간 배정이 필요해지기 전에는 주차별 TODO 복제나 새 연결 테이블을 만들지 않는다.

### 독립 활동과 시간 블록의 추가 정보

- 독립 활동 `activity_entries`는 후속 설계다. 활동명·실행 날짜/소요·카테고리·메모·소유권을 검토하되
  이번에는 파일/테이블/SQL/저장 액션을 만들지 않았다.
- 기존 TodoTimeBlock에는 개별 활동명·대표 카테고리·메모가 없다. 활동명/태그는 TODO에서 읽는다.
  시안의 블록 메모는 메모리에만 있다. 실제 보존에는 별도 필드/모델 승인과 검증이 필요하다.
- Event는 실제 HH:mm과 계획이 같은 date에 의존한다. 계획일과 실행일을 따로 옮기려면 실행일 또는
  시작/종료 timestamp·시간대 모델을 검토해야 한다. 시안은 실제가 있는 Event의 날짜 이동을 막는다.
- 자정 통과·레거시 실행일 모호성·옛 주차 키의 제약은 STEP 1 보고서 그대로다.
- XP의 누적 보장/완료 취소/중복 보상 방지는 별도 정책 문제다. 시안에서 XP 원장이나 보상 코드를 만들지 않았다.

## 10. 접근 방법과 산출물

기존 체크아웃 `/workspace/my-planner`를 사용한다. 별도 worktree·새 의존성·운영 환경변수는 필요 없다.

### 추천 최소안 — DB 변경 없이 신규 입력부터 구분

- 할 일 등록·수정의 선택 옵션을 **목표 연결 / 시간 분석 태그 / 일반 태그**로 분리한다. 목표를 고르지 않아도 태그를 선택할 수 있고, 태그 없이도 목표를 연결할 수 있다. 목표를 바꿔도 태그를 자동 변경하지 않는다.
- 제목만으로 등록하는 흐름은 유지한다. **시간 분석 태그는 선택 사항·최대 1개**이며, 선택하지 않은 실제 기록은 미분류로 표시한다. 일반 보조 태그는 여러 개를 선택한다.
- 대표 선택 후보는 `trackTime=true`, 보조 후보는 `trackTime=false`인 기존 태그다. 같은 ID를 중복 저장하지 않는다. 대표를 바꾸면 사용자가 고른 대표 ID만 교체하고 보조/목표는 보존한다. 저장 배열의 첫 원소를 대표라는 숨은 규칙으로 사용하지 않는다.
- 저장은 기존 `Todo.tags`와 확인 저장 액션을 사용한다. 이 제약은 새 모아모아 입력의 UX/검증에 적용하며 기존 공통 `addTodo`에 다중 추적 태그 금지 규칙을 넣어 레거시 호출을 깨뜨리지 않는다.
- 추적 태그가 하나인 기존 TODO는 대표 선택으로 표시한다. 없는 경우 ‘선택 안 함 / 실제 시간 미분류’, 둘 이상이면 **기존 방식 · N개 태그에 균등 분할**로 표시한다. 기존 배열은 읽기·제목 수정·완료 체크만으로 축소하거나 재저장하지 않는다.
- 레거시 다중 태그를 대표 방식으로 바꾸려면 별도 명시적 편집으로 선택하도록 한다. 제거될 태그 연결과 과거 통계 영향도 안내한다. 기존 추적 태그를 보조로 남기려고 전역 `trackTime`을 자동 OFF로 바꾸지 않는다.
- 태그 생성 시 용도(시간 분석 / 일반)를 명시한다. 이름·색상·기존 ID는 재사용하며, 자동 생성이나 미리보기만으로 DB 쓰기가 생기지 않게 한다. 생성 실패 시 TODO에서 존재하지 않는 태그를 저장하지 않고 초안을 유지한다.

**최소안의 한계:** `trackTime`은 태그의 전역 성격이다. 같은 태그를 TODO A에서는 대표, TODO B에서는 시간에 영향을 주지 않는 보조로 사용하는 것은 위 구조로 표현할 수 없다. 현재 블록은 TODO 태그를 참조하므로 TODO 태그 수정이나 전역 집계 ON/OFF는 과거 시간 통계에도 영향을 준다. 시간 기록 당시의 분류를 고정하는 스냅샷도 현재 없다. 사용 중인 태그의 용도 변경은 영향 확인 없이 허용하지 않는 방향으로 설계한다.

TODO별로 자유로운 대표/보조 역할이나 ‘분석용 태그를 보조로도 선택’을 원한다면 별도 후속 모델 검토가 필요하다. 예를 들어 선택적 `primaryTimeTagId`와 레거시 분할/대표 방식의 명시적 구분을 두고, 역할이 없는 기존 행은 균등 분할로 읽는 방식이다. nullable 대표 필드만으로는 ‘레거시’와 ‘새 방식에서 대표 미선택’을 구분할 수 없으므로 구분 정책까지 함께 설계해야 한다. 이 안은 **이번에 필드·마이그레이션을 추가하지 않으며**, 필요성이 확정된 뒤 별도 승인·격리 검증 대상으로 남긴다.

### 태그 관리와 저장 신뢰성 — STEP 3B-2

기존 `addTag`/`updateTag`는 낙관적으로 상태를 바꾸고 저장 결과를 기다리지 않는다. `deleteTag`는 태그를 제거하며 **모든 TODO를 upsert**하고, 일정의 태그 참조는 함께 정리하지 않는다. 그대로 새 모아모아의 신뢰할 수 있는 관리 동작으로 간주하지 않는다.

- 기존 모델·DB 변환·관리 UI를 재사용하되 태그 CRUD에 확인 저장/명시적 재시도의 공통 패턴을 작게 적용한다. 등록은 안정적인 생성 ID로 중복 방지, 실패는 초안과 확인된 상태 유지, 반복 클릭 방지를 검증한다. 새 전송 계층을 복제하지 않는다.
- 태그 이름·색상 변경과 집계 용도 변경을 구분한다. 용도 변경은 전체 참조 TODO/일정 및 과거 통계에 영향을 줄 수 있음을 안내하고 명시적으로 확인한다.
- 미사용 태그 삭제를 먼저 지원하고, 사용 중인 태그는 연결 해제/분류 변경을 명시적으로 진행한 뒤 삭제하는 보수적 흐름을 우선한다. 삭제 검증은 로드된 일부 기간만 보고 ‘미사용’으로 단정하지 않으며 전체 참조 확인 방안을 격리 환경에서 검토한다. 확인할 수 없다면 안전하게 삭제를 보류한다.
- 전체 TODO 재저장이나 페이지 진입 중 참조 정리를 하지 않는다. 여러 행 정리의 부분 실패·원자성을 클라이언트에서 보장한다고 표시하지 않는다. 안전한 연결 삭제에 DB 제약/트랜잭션 변경이 필요하면 별도 승인안으로 분리한다.
- TODO·캘린더·분석에서 동일 Provider 태그 목록과 ID를 사용한다. 목표 연결이나 화면 카테고리에 맞춰 태그를 자동 생성/복제하지 않는다.

### 실제 시간과 통계 — STEP 3B-3

1. 일간·주간·월간 전환과 날짜/기간 이동은 동일한 `aggregateActivity` 결과를 사용한다. 일간은 시작일=종료일로 호출하고, 기존 hook의 기간/기준 날짜 지원만 확장한다. 논리적 오늘과 저장된 실제 작업일의 경계 규칙을 재사용한다.
2. TODO 실적은 날짜별 `todo_time_blocks` 우선, 기존 `do_*`는 공통 중복 방지 규칙대로 읽는다. 이벤트도 계획이 아닌 실제 실행 시각만 사용한다. 수면·운동 로그를 자동 중복 합산하지 않는다.
3. 새 단일 추적 태그는 실제 60분이면 해당 태그 60분이다. 일반 보조 태그에는 시간을 배분하지 않는다. 레거시 추적 태그 2개는 기존대로 각각 30분이다. 첫 태그 우선이나 반올림 후 합산으로 바꾸지 않는다.
4. **태그별 분류 시간 / 미분류 실제 시간 / 실제 기록 총시간**을 구분한다. 현재 `totalMinutes`는 분류 시간, `coverage.recordedMinutes`는 계산 가능한 실제 총시간이라는 계약을 유지한다. 미분류는 `coverage.unclassifiedMinutes`와 상세 사유(태그 없음·일반 태그만·알 수 없는 ID·TODO 참조 없음)를 표시한다.
5. 시각/날짜가 모호해 계산할 수 없는 기록은 미분류 분량에 추정 합산하지 않고 ‘확인 필요 N건’으로 별도 표시한다. 유효한 실적을 태그가 없다는 이유로 실제 총시간에서 버리지 않는다.
6. 완료 체크는 상태/길이 0 완료 마커만 변경한다. 계획 시간이나 기본 30분을 실적으로 생성하지 않는다. 태그별 건수와 실제 시간은 별도 지표다.
7. 할 일 목록, 캘린더, 분석 상세는 동일 TODO ID로 열고 수정하며 중복 저장하지 않는다. 태그 변경이 과거 분류에도 반영되는 현재 동작을 명시한다.

| 단계 | 필수 확인 |
| --- | --- |
| 3B-2 입력 | 제목만 등록, 대표 0/1개·보조 여러 개, 목표와 독립 선택, 동일 ID 보존, 복수 추적 태그의 명시적 처리, 레거시 일반 편집 시 배열 보존 |
| 3B-2 관리 | 생성·이름/색상 수정·집계 용도 변경·삭제의 확인 저장, 실패/재시도·중복 방지, 참조 확인·과거 통계 영향 안내, 전체 TODO 자동 upsert 없음 |
| 3B-3 집계 | 실적 60분+대표 1개+보조 2개 → 대표만 60분, 레거시 추적 2개 → 각 30분, 실적+태그 없음 → 미분류 60분 |

| 공통 | TODO·캘린더·분석의 태그/목표/완료 상태 일치, 삭제/알 수 없는 참조 진단, 새로고침·다른 기기 반영, 실패 시 확인된 데이터 유지 |

후속 테스트는 기존 메모리 전송 계층 또는 격리 Supabase를 사용한다. 이 명세 반영 과정에서 운영 DB 조회·쓰기, 태그 변환 및 기존 데이터 마이그레이션은 수행하지 않는다.

## STEP 3B-2 구현 현황

앞의 태그·시간 항목은 STEP 3B-1 시점의 후속 계획이며, 현재는 개발 전용 `/__moamoa-todos`에 할 일 목록/입력/상세, 태그 선택·확인 관리, 주간 목표 연결·해제, TODO 연결 수동 시간 기록을 구현했다. 반복의 복잡한 편집·삭제·수동 시간 기록과 저장 필드가 없는 메모는 비활성화하고 이유를 안내한다. 새 UI·DB 스키마를 실제 제품 기본 경로에 배포하거나 기존 데이터를 변환하지 않았다.

STEP 3B-3은 이미 연결한 TODO 소요 기록을 다시 만드는 작업이 아니라 **독립 활동 모델과 일·주·월 분석 확장**에 집중한다. 기록 시점의 분류 고정에는 블록/활동별 태그 ID·분배 비율 스냅샷 또는 버전 모델이 필요하며 별도 승인 대상으로 유지한다. 사용자에게 과거 통계가 바뀔 수 있음을 표시하고 현재 태그로 과거 분류를 추정해 채우지 않는다.

구현 파일, 버튼별 검증, 삭제 경쟁 조건과 실제 Supabase 검증 범위는 [STEP 3B-2 보고서](MOAMOA_STEP3B_TODO_TAGS.md)를 따른다.

## STEP 3B-3 개발 경로 반영 (2026-10-22)

이 절은 앞선 STEP 3B-3 제안의 현재 구현 상태를 보완한다. 프로덕션 공개/DB 적용을 의미하지 않는다.

- 기록 메뉴의 개발 경로는 `/__moamoa-records`. 실제 Auth/Provider를 사용하며 프로토타입 fixture를 가져오지 않는다.
- 일간/주간/월간·이전/다음·날짜, 실제 소요 합계·전체 분포·일별 변화·이전 기간 카테고리 비교·미분류·상세 목록을 공통 aggregateActivity로 연결했다.
- 시간 빠른 기록은 독립 활동과 할 일 연결을 구분한다. 활동명/분/카테고리/날짜가 기본이며 메모/실제 시각은 선택 확장이다. 소요만 알면 시각을 만들지 않는다. 새 활동을 위한 TODO는 생성하지 않는다.
- 독립 활동은 activity_entries, TODO 연결은 todo_time_blocks만 사용한다. 새 분류는 ID/이름/색상/비율 스냅샷을 보존하고, 기존 스냅샷 없는 기록은 현재 태그 fallback으로 명시한다. 과거 일괄 추정 보정은 하지 않는다.
- 저장 중/확인 성공/실패·명시적 재시도를 공통 SaveCoordinator로 구분한다. 스키마 미적용/조회 실패는 저장 불가 또는 합계 미확인 안내를 표시한다. 오프라인 영구 저장을 지원한다고 표시하지 않는다.
- 오늘과 할 일의 실제 시간 합계도 같은 활동을 포함한다. 기존 홈 빠른 TODO는 유지하며 그 시트에서 시간 기록으로 이동한다.
- 실제 시각이 겹쳐도 자동 삭제/합산 차감을 하지 않는다. 자정 통과 기록은 선택한 기록 날짜에 전체 소요를 귀속한다. 수면/운동 라이프 로그를 자동 시간 원천으로 추가하지 않는다.
- 기록 안의 음식·문화/음악·독서 링크는 기존 경로를 연다. STEP 3B-4에서 기존 사진·ID·API를 유지한 채 새 UI를 연결하고 수동 입력을 우선 보장한다.
- [상세 구현/제약/검증 보고](MOAMOA_STEP3B_TIME_ANALYSIS.md), [미적용 SQL 초안](sql-drafts/moamoa_activity_entries.sql), [캡처](screenshots/moamoa-time/README.md)를 검토한다.

미해결 UX 결정: 과거 snapshot 없는 기록의 사용자 주도 분류 고정 절차, 이름을 바꾼 동일 카테고리의 합계 라벨, 여러 날 활동을 명시적으로 분할 입력하는 흐름, 겹침 후보 확인 후 사용자가 직접 정정하는 흐름. 프로덕션 경로 공개와 SQL 적용은 별도 승인 대상이다.
