## 2. 디자인 제안: Cozy Life Diary + Tiny RPG

“나의 하루, 시간, 목표, 습관, 경험을 하나씩 모아가며 성장하는 귀여운 라이프 아지트.”

기록량이나 성과보다 **다시 들어오기 편한 공간**을 우선한다. 앱을 열면 이번 주의 방향을 먼저 보고,
한 가지를 체크하거나 짧게 기록한 뒤 나갈 수 있어야 한다. 모든 기능을 홈에 나열하지 않는다.

| 1차 메뉴 | 핵심 역할 | 2차 구조 | 첫 화면에서 줄이는 것 |

| 퀘스트 | 같은 TODO를 실행 관점으로 보기 | 오늘 / 이번 주 / 날짜 미정 × 업무·라이프·개인 프로젝트 | 별도의 퀘스트 행·복제된 완료 상태 |
| 기록 | 지금 남길 것을 고르고 나를 이해 | 즐겨 기록 4개 → 시간 분석 → 생활 기록/회고 | 처음부터 모든 건강 기능 나열 |
| 나의 정원 | 성장과 장기 방향을 돌아보기 | 캐릭터·성장, 월간·연간 목표, 씨앗/버킷리스트, 하이라이트 | 꾸미기 상점·재화·랭킹 |

모바일은 하단 5개 메뉴, PC는 왼쪽 5개 메뉴를 사용한다. **빠른 기록은 메뉴가 아니라 전역 동작**이다.
모바일 오른쪽 아래의 작은 기록 버튼, PC 상단 버튼과 화면 안 추가 진입점이 같은 시트를 연다.
기존 서비스의 메뉴/홈은 그대로 두었다.

기록 내부 분류는 시간 / 건강(수면·운동·컨디션·생리·셀프케어) / 마음(감정·일기) / 회고로 묶는다.
처음에는 시간·마음·수면·하루 한 줄만 바로 보이고 나머지는 펼쳐서 찾는다. 실제 사용 빈도로
즐겨 기록 순서를 조정하는 것은 후속 검토이며 이번 시안에서 설정 기능을 만들지는 않았다.

## 4. 화면별 설계

### 오늘 — 모바일 우선

1. 날짜·짧은 인사와 작은 캐릭터. 성장 상태는 작은 보조 표시다.
2. 실제 활동 시간과 데일리 회고 진입을 한 줄 요약으로 제공한다.
3. **이번 주 목표**를 첫 화면 안에 표시한다. 두 목표의 개별 진행률과 전체 가중 진행률을 구별한다.
4. 오늘의 핵심 TODO는 기존 `isTop3` 기준 최대 3개다. 추가한 일반 TODO는 퀘스트의 전체 목록에서 확인한다.
5. 아래에는 오늘의 약속 요약, 카테고리별 실제 시간, 조금 더 넓은 회고 진입을 배치한다.
6. 기록 버튼은 스크롤 중에도 접근 가능하다. 홈에서 목표 편집이나 모든 로그 입력을 요구하지 않는다.

390×844 렌더에서 주간 목표는 스크롤 없이 보인다. “홈 진입 10초 안에 목표 확인”은 설계 목표다.
실제 사용자 대상 시간 측정을 완료한 것은 아니다. 아래 카드는 자연스러운 세로 스크롤로 확인한다.

PC는 인사/목표/핵심 TODO를 왼쪽, 캐릭터/일정을 오른쪽에 배치한다. 캐릭터가 업무 정보를 가리지 않으며
카테고리 시간과 회고를 아래에서 이어서 본다. 화면 폭이 달라도 데이터와 완료 기준은 같다.

### 캘린더 — 같은 자료의 다른 보기

**주간 일정**은 PC에서 월~일 7열과 PLAN/DO 두 레인을 사용한다. 계획은 옅은 카테고리색,
실제는 세이지 레인으로 구별한다. 일정을 누르면 전체 제목과 날짜·시간을 편집하는 시트가 열린다.
좁은 시간 블록은 제목을 축약하고 툴팁/접근 가능한 전체 이름을 제공한다. 축약은 데이터 잘림이 아니다.

모바일은 7열을 억지로 축소하지 않고 요일 선택 후 하루의 PLAN/DO를 본다. 계획을 옮겨도 실제 시간
블록은 이동하지 않는다. 이 시안은 **클릭 후 날짜/시간 변경**을 구현했으며 드래그/리사이즈는 구현하지 않았다.
실제 적용 시 기존 Timeline과 WeekAllDayLane의 이동 동작을 먼저 재사용한다.

실제 기록이 있는 기존 Event에는 별도 실행일이 없다. 날짜 변경으로 실제 기록까지 이동하는 것처럼
시연하지 않기 위해 해당 일정의 날짜 이동을 제한했다. 실제 기록 없는 일정과 TODO 계획은 날짜 이동을
시연할 수 있다. 필요한 모델 확장은 7절에 정리했다.

**주간 플래너**는 PC에서 목표/날짜 미정/시간 요약을 왼쪽에, 월~일 노트 카드를 오른쪽에 둔다.
빈 여덟 번째 칸은 “모든 칸을 채우지 않아도 괜찮다”는 여백으로 사용한다. 아래에는 전체 TODO 펼침,
습관 트래커, 주간 회고가 이어진다.

모바일은 상단 조작부를 압축하고 목표 → 요일 선택 → 선택일 계획 → 날짜 미정 → 습관 → 시간/회고로
이어진다. 7일 카드를 모두 길게 쌓지 않는다. “이번 주 전체 할 일”을 펼치면 주간 전체 자료를 본다.
습관은 모바일에서 이름 아래 7개의 넓은 체크 칸을 두어 최소 약 44×44px의 터치 영역을 확보했다.
미래 날짜 체크는 비활성화하며 미기록은 빈칸으로 표현한다.

**월간/일간**은 탐색 구조와 기본 레이아웃을 제시한다. 모바일 월간은 아주 작은 제목 대신 항목 수를
표시하고 날짜를 눌러 일간 전체 내용을 확인한다. 고급 반복 편집·겹침 배치·확장 시간축은 상세 시안에서 제외했다.

### 퀘스트

- 오늘 / 이번 주 / 날짜 미정과 카테고리 필터를 조합한다.
- 하나의 TODO ID를 여러 화면에서 표시한다. 전용 Quest 테이블을 만들지 않는다.
- 연결 목표 진행률은 STEP 2 공통 계산을 사용한다. 완료 체크는 확인 후 표시한다.
- 수동 완료와 연결 TODO 계산, 취소·백로그·날짜 미정의 기준을 바꾸지 않는다.
- 완료 축하는 작은 문구로 충분하며 자동 화면 이동·큰 팝업·XP 차감을 하지 않는다.

### 기록과 빠른 기록

빠른 기록은 기본 **할 일** 탭이다. 제목만 필수이며 날짜는 오늘/미정/다른 날짜, 카테고리와 목표 연결은
필요할 때 펼친다. 날짜를 선택한 요일 카드에서 추가하면 그 날짜를 미리 채운다. 날짜 미정 카드에서는
날짜를 비워둔다.

**시간** 탭은 연결할 TODO(활동명) → 소요 시간(15/30/60분 또는 직접 입력) → 날짜 순이다.
대표 카테고리는 TODO의 태그를 보여주며 멋대로 태그를 교체하지 않는다. 기존 복수 추적 태그의 시간 분할은
계산 엔진에 그대로 맡긴다. 메모 칸은 시안이며 기존 시간 블록에 메모 컬럼이 있는 것처럼 가정하지 않는다.

시간 시트의 반영 버튼은 필드 스크롤과 분리해 항상 보인다. 날짜/메모/다른 옵션은 필요한 경우에만
스크롤한다. 익숙해진 사용자가 10초 이내 기록하는 것을 목표로 하되 이번 단계에서 인간 사용성 측정을
수행한 것은 아니다.

**독립 활동**은 `후속 설계`로 표시하고 반영 버튼을 비활성화했다. TODO 없이 실제 저장되는 기능처럼
보이게 하지 않는다. 활동 기록을 만들기 위해 숨겨진 가짜 TODO를 생성하지도 않는다.

시간 분석은 일간/주간/월간을 전환하며 같은 `aggregateActivity`를 사용한다. 계획은 실제 시간에
합산하지 않는다. 수면·운동 등의 생활 로그를 활동 시간에 자동으로 다시 더하지 않는다.

수면·마음·일/주/월 회고는 짧은 입력과 메모리 반영만 시연한다. 다른 생활 기록은 분류와 탐색 위치만 제안한다.

### 나의 정원

캐릭터 한 명과 성장 단계 표시, 월간/연간 방향, 버킷리스트/씨앗, 작은 성취를 배치한다. 초기 시안의
레벨·XP 수치는 고정 예시이며 TODO 체크로 실서비스 XP를 바꾸지 않는다. `Lv.2`, 140/800은 기존
레벨 곡선에서 총 XP 940인 경우의 예시다.

기존 ProfileView는 완료 수·습관·현재 streak 등에서 XP를 계산한다. 현재 streak 보너스가 바뀌면 총 XP도
변할 수 있으므로, “쉬어도 경험치가 내려가지 않는다”는 새 약속을 실제로 보장하려면 XP 정책의 별도
검토가 필요하다. 이번 단계에서는 기존 XP 코드나 데이터 모델을 변경하지 않았다.

## 5. 주요 사용자 흐름과 저장 상태

| 흐름 | 시연 동작 | 실제 구현 시 연결 |
| --- | --- | --- |
| 하루 시작 | 오늘 → 상단 목표 확인 → 핵심 TODO 체크 → 짧은 축하 | 같은 TODO ID, `updateTodo`, `weeklyRollup` |
| 빠른 할 일 | 기록 버튼 → 제목 → 모아두기 | `addTodo`의 안정적인 생성 ID와 확인 결과 |
| 시간 기록 | 시간 탭 → 연결 TODO → 분 단위 소요 → 모아두기 | 기존 `todo_time_blocks`, 공통 시간 집계 |
| 한 주 정리 | 캘린더 → 주간 플래너 → 요일/날짜 미정 → 습관 → 회고 | 기존 TODO/Event/Habit/WeeklyReview |
| 계획 이동 | 시간표/퀘스트의 편집 → 날짜·시각 → 확인 | 기존 날짜 이동 헬퍼와 확인 저장 액션 |
| 하루 마무리 | 홈 회고 → 한 문장 → 작은 기록 | 기존 데일리 회고 필드 |
| 실패 복구 | 시안 옵션의 다음 반영 실패 → 입력 유지 → 재시도 → 완료 | STEP 2의 요청 상태·동일 ID·동일 payload |

프로토타입 반영은 약 450ms 지연한 **메모리 시연**이다. 성공 전에는 이전 값/초안을 유지한다.
실패를 성공처럼 체크하지 않으며 재시도는 동일 ID를 사용한다. 시트 안 알림은 모달의 접근성·포커스
범위 안에 두었다. 실패 후 재시도 성공 시에는 완료/닫기를 표시한다.

운영 제품의 오프라인 저장이나 새로운 저장 보장을 구현한 것이 아니다. 새로고침/샘플 초기화는 이 시안의
메모리만 지운다. 브라우저 localStorage/sessionStorage나 사용자 인증 정보를 초기화하지 않는다.

## 7. 데이터 모델 검토 — 변경 실행 없음

### 현재 모델로 가능한 것

- 월간 목표 → 주간 목표는 `monthlyGoalId`, 주간 목표 → TODO는 `weeklyGoalId`를 유지한다.
- 오늘/플래너/퀘스트는 같은 Todo 행을 조회하고 같은 완료 상태를 표시한다.
- TODO에 연결한 소요는 기존 `todo_time_blocks`의 `todoId`, `date`, `elapsedSec`를 사용한다.
  시각 없는 소요도 분석에 포함되지만 시간표 위치를 임의로 만들어 그리지 않는다.
- 주간 목표에 연결된 날짜 미정 TODO는 목표의 `weekKey`로 주간 목록에 포함할 수 있다.
- 습관은 기존 체크 날짜를 요일별로 펼친다. 새 체크 테이블을 화면별로 만들지 않는다.

### 특정 주에만 배정된 날짜 미정 TODO

현재 Todo에는 독립 `weekKey`가 없다. `BrainstormItem.weekKey`는 아이디어용이며 TODO의 주차 필드로
대신 쓰면 의미가 달라진다. 주간 목표 연결을 억지로 만들거나 가짜 날짜를 넣는 것도 권장하지 않는다.

MVP 확장 후보는 nullable `Todo.plannedWeekKey` / DB `planned_week_key` 한 필드다. **이름·스키마·SQL은
확정하지 않았고 구현하지 않았다.** 추천 읽기 규칙은 다음과 같다.

1. 날짜가 있으면 해당 날짜의 주간 일정/플래너에 배치한다.
2. 날짜가 없고 명시적 plannedWeekKey가 있으면 그 주의 날짜 미정 영역에 배치한다.
3. 둘 다 없으면 기존 연결 주간 목표의 weekKey로 보완한다.
4. 어떤 주에도 속하지 않으면 전역 날짜 미정 목록에 남긴다.

목표 진행률은 배치 주간으로 TODO를 다시 거르지 않고 STEP 2 연결 관계를 따른다. 날짜 지정/해제 시
명시적 주차를 보존할지 갱신할지는 UX 결정 후 정의해야 한다. 기존 데이터 일괄 보정은 하지 않는다.
다중 주간 배정이 필요해지기 전에는 주차별 TODO 복제나 새 연결 테이블을 만들지 않는다.

### 독립 활동과 시간 블록의 추가 정보

- 독립 활동 `activity_entries`는 후속 설계다. 활동명·실행 날짜/소요·카테고리·메모·소유권을 검토하되
  이번에는 파일/테이블/SQL/저장 액션을 만들지 않았다.
- 기존 TodoTimeBlock에는 개별 활동명·대표 카테고리·메모가 없다. 활동명/태그는 TODO에서 읽는다.
  시안의 블록 메모는 메모리에만 있다. 실제 보존에는 별도 필드/모델 승인과 검증이 필요하다.
- Event는 실제 HH:mm과 계획이 같은 date에 의존한다. 계획일과 실행일을 따로 옮기려면 실행일 또는
  시작/종료 timestamp·시간대 모델을 검토해야 한다. 시안은 실제가 있는 Event의 날짜 이동을 막는다.
- 자정 통과·레거시 실행일 모호성·옛 주차 키의 제약은 STEP 1 보고서 그대로다.
- XP의 누적 보장/완료 취소/중복 보상 방지는 별도 정책 문제다. 시안에서 XP 원장이나 보상 코드를 만들지 않았다.

## 10. 접근 방법과 산출물

기존 체크아웃 `/workspace/my-planner`를 사용한다. 별도 worktree·새 의존성·운영 환경변수는 필요 없다.
현재 개발 서버는 5174 포트로 실행했다. 프로세스가 종료된 후에는 다음 명령으로 다시 시작한다.

```bash
cd /workspace/my-planner
npm run dev -- --host 0.0.0.0 --port 5174 --strictPort
```

대체하지 않는다. HTML 파일을 로컬 파일로 직접 여는 대신 Vite가 제공하는 경로를 사용해야 한다.

시안 옵션은 상단 샘플 안내 또는 PC 사이드바에서 연다. 다음 반영 실패 시연/샘플 초기화를 선택할 수 있다.
상태는 탭 이동 중 공유되지만 새로고침하면 샘플로 돌아온다. 모달은 ESC·포커스 트랩·초점 복귀를 지원한다.

구현 파일은 다음과 같이 분리했다.

- `prototypes/moamoa.html`: 개발 전용 독립 HTML.
- `vite.config.ts`: 개발 서버에만 해당 HTML을 제공하는 미들웨어 14줄 추가.
- `src/prototypes/moamoa/`: 샘플 데이터/메모리 상태, 공용 표시 요소, 화면, 시트, 전용 CSS.
- `scripts/test/moamoa-prototype.test.mjs`: 실제 Vite 설정/진입점의 브라우저 검증·스크린샷 생성.
- `docs/MOAMOA_V01_UX_SPEC.md`, `docs/prototypes/moamoa/`: 명세·렌더 산출물.

프로토타입의 9개 테스트는 상위 1개 + 하위 8개이며, 위 테스트 수에 중복해서 더하지 않는다.
렌더와 상호작용을 실제 Chromium에서 실행했고 대표 화면을 직접 열어 검토했다. 색 대비 인증이나
실기기 iOS/PWA·화면 읽기 도구 사용성 검증까지 완료한 것은 아니다. 조밀한 시간표의 축약 항목·메타데이터는
일반 본문보다 작은 글씨를 사용하므로 실제 사용자 검토에서 밀도/축약 정도를 확인해야 한다.

기존 렌더 경고는 라벤더 색상 정보성 경고다. PC의 모바일 전용 시간 블록 탭/일부 메뉴와 모바일의
특정 일정 편집/종일 전환·반복 편집 팝업은 기존 하네스에서 대상 요소를 찾지 못해 생략했다.
500kB 초과 Production 번들 경고도 기존 상태 그대로다.

초기 브라우저 실행에서는 기본 5173 포트와 직접 시작한 개발 서버가 충돌했다. 제품 오류가 아니라
실행 환경 충돌이었으며, 직접 시작한 서버만 종료하고 검토 서버를 5174로 옮긴 뒤 전체 검사를 통과했다.
