## 3. 목표 진행률 Before / After

| 상황 | Before | After |
| --- | --- | --- |
| 홈과 목표 화면 | 홈은 주간 목표의 raw `done` 중심, 목표 화면은 연결 TODO 중심 | 모두 `weeklyRollup` / `monthlyRollup` 사용 |
| 주간 목표의 수동 완료 + 미완료 TODO | 체크·진행률이 충돌할 수 있음 | 유효한 TODO가 있으면 TODO 결과 우선, 수동 토글 비활성화 |
| 월간 목표의 수동 회고 + 하위 목표 | 회고의 달성과 계산된 진척이 혼동될 수 있음 | 하위 주간 목표 가중 집계 우선, 주관적 배지는 `회고:`로 구분 |
| 자식이 없는 목표 | 수동 완료 해석이 화면마다 다름 | 주간 `done`, 월간 `retroStatus === 'done'`을 1/1 또는 0/1로 표시 |
| 199개 완료 / 200개 TODO | 반올림으로 100% 표시 가능 | 미완료가 있으면 최대 99%, 실제 전부 완료할 때만 100% |

계산 규칙:

1. `weeklyGoalId`로 연결된 TODO 중 `cancelled`, `backlog`를 분모/분자에서 제외한다.
   `active`, `inProgress`, `snoozed`는 분모에 포함하며 `done`만 분자에 포함한다.
   날짜가 없거나 목표 주간 밖에 있어도 **명시적으로 연결된 TODO는 포함**한다.
2. 유효 TODO가 하나 이상이면 TODO 완료율과 `completed`가 단일 기준이다.
   raw `WeeklyGoal.done` 값은 변경·초기화하지 않는다. 모두 취소/백로그가 되면 수동 기준으로 돌아간다.
3. 유효 TODO가 없으면 주간 수동 완료를 0/1 또는 1/1로 계산한다.
4. 월간은 연결 주간들의 분자·분모 합으로 계산한다. 예: 주간 A 1/3, 수동 완료 B 1/1 → 월간 2/4=50%.
   하위 주간이 없으면 기존 월간 회고의 `done`만 수동 100%로 해석하며 partial/missed/미작성은 0%다.
5. 홈 전체 요약도 같은 가중 합을 사용한다. 연간의 기존 집계 역시 수정된 월간 공통 결과를 따른다.
6. 목표가 없는 전체 요약은 0%다. 원본 TODO·주간/월간 연결이나 완료 플래그를 재저장하지 않는다.

실제 대시보드·목표 페이지·주간 회고를 동일한 부분 완료 시드로 띄워 같은 목표의 값이 일치하는지
브라우저에서 비교한다. 모바일 목표 상세도 같은 부분 완료 값으로 비교하고 PC/모바일 상세 화면을 캡처했다.
기존 주간 화면과 사이드 패널도 공통 함수를 소비한다.
모바일의 별도 빠른 캡처 홈에는 목표 카드 자체가 없으므로 새 카드를 추가하지 않았다. STEP 3에서
새 홈을 만들 때 이 계산 결과를 그대로 사용해야 한다.

## 4. 저장 실패와 재시도

### 확정된 상태만 화면에 반영

핵심 TODO 등록/단건 변경/완료, 주간 목표 등록/수정/완료, 월간 목표 등록/수정/회고에
동일한 `SaveCoordinator` → `confirmedWrites` → 서버 반환 행 반영 패턴을 적용했다.

- 저장 중/저장됨/실패를 기존 테마의 공통 알림으로 표시한다.
- 기존처럼 먼저 완료 처리한 뒤 실패를 로그에만 남기지 않는다. 저장 중에도 마지막 확정 값을 유지한다.
- 등록 API는 `Promise<string | null>`, 수정·완료 API는 `Promise<boolean>`을 반환한다.
  실패하면 입력을 지우거나 주요 등록 모달을 자동으로 닫지 않는다.
- DB의 반환 행을 확인해야 성공이다. 권한 때문에 수정 행이 보이지 않거나 결과가 없으면 실패다.
- 수정은 실제 바뀐 컬럼만 전송한다. 다른 기기에서 바꾼 무관한 필드를 오래된 전체 행으로 덮어쓰지 않는다.
- UI에 DB 원시 오류·입력 payload를 노출하지 않는다.

### 중복 방지와 안전한 재시도

- 같은 엔티티·같은 의도의 저장 중 요청은 하나의 Promise로 합친다. 다른 변경은 저장 중임을 알리고 거절한다.
- 폼별 생성 UUID를 저장 확인 전까지 유지한다. 캡처/만다라트/브레인스토밍 전환은 원본 기반 ID를 사용한다.
- 생성은 기존 PK에 `ON CONFLICT DO NOTHING` 후 결과를 확인한다. 응답만 유실됐어도 같은 ID로 재시도한다.
  이미 같은 ID가 다른 내용이면 덮어쓰거나 새 행을 만들지 않고 충돌을 알린다.
- 재시도는 캡처한 동일 ID·동일 payload/절대 상태 변경을 다시 전송한다. 토글 함수를 다시 실행하지 않는다.
- 네트워크/오프라인·408·429·5xx만 명시적 재시도를 제공한다. 권한·인증·제약 오류는 바로 재시도하지 않는다.
- 자동 재시도나 영속 오프라인 저장함은 없다. 연결 복구는 재조회만 하고 미저장 요청은 사용자가 재시도한다.
- 재시도에 성공해도 원래 폼의 제출 Promise를 되살리지는 않는다. 유지된 초안의 다시 제출은 같은 ID를 확인하므로
  중복 생성 없이 폼을 닫을 수 있다. 입력 내용을 바꿨는데 같은 ID가 이미 저장됐으면 충돌을 표시한다.
- 실패 알림을 닫는 것은 서버 저장 취소가 아니다. 새로고침은 서버 값을 다시 읽는다.

### 다른 저장 경로와 동기화

- TODO의 Top3 변경, 타이머 시작 상태 변경도 공통 단건 저장 경로를 사용한다.
- 타이머 정지/완료는 기존 시간 블록을 먼저 확인 저장하고 TODO의 `do_*`/상태를 확인 저장한다.
  둘 다 확인하기 전에는 타이머를 정리하지 않고 일시정지 상태와 세션 ID를 기존 localStorage에 유지한다.
  세션 ID를 시간 블록 PK로 사용하므로 두 번째 쓰기가 실패해도 재시도 시 시간 블록이 늘어나지 않는다.
  타이머 시작 저장 실패 후 공통 재시도는 TODO만 저장하며 타이머를 몰래 시작하지 않는다.
- 만다라트의 TODO·주간/월간 전송은 출처와 부모 연결을 유지하며 확인 저장 후에만 성공 알림을 낸다.
  연간 목표 전송은 이번 핵심 범위에 포함하지 않았다.
- 브레인스토밍의 TODO 전환은 TODO 저장 확인 전에는 원본을 지우지 않는다.
  공통 재시도 후 전환 버튼을 다시 누르면 같은 TODO를 확인하고 원본 정리를 이어간다.
- 기존 Supabase Realtime 구독을 유지한다. 핵심 세 테이블은 읽기 실패로 확정 행을 빈 배열로 지우지 않는다.
  저장 중/실패로 미확정인 행은 로컬 확정 값을 잠시 유지하고 다른 행은 원격 값을 반영한다.
  저장 상태가 바뀌기 전에 시작한 오래된 재조회 응답은 버린다. 화면 복귀/온라인 복구 때도 재조회한다.

모두 통과했다. 이 일시적 실패를 운영 앱 오류나 기존 오류로 단정하지 않았다. 추가 모바일 검사에서는 PC에서 전환한 탭이
별도로 마운트되는 모바일 outlet에 유지된다고 가정해 한 번 타임아웃이 났다. 모바일 탭을 명시적으로
선택하도록 검사 코드를 수정한 뒤 통과했다. 제품 코드를 이 테스트 가정에 맞춰 변경하지 않았다.

## 6. 회귀 위험과 미해결 사항

1. **완료 표시의 의미가 바뀐다.** raw 주간 done이 true여도 연결 TODO가 미완료면 계산상 미완료다.
   원본 플래그는 유지하며 유효한 TODO가 없어지면 수동 기준으로 돌아온다. 월간 수동 회고도
   하위 주간의 계산을 덮어쓰지 않는다. 기존에 보던 숫자가 바뀔 수 있지만 데이터 이행은 없다.
2. **저장 확인까지 반응 시간이 보인다.** 완료 체크는 서버 확인 전까지 이전 값이며 공통 알림에 저장 중이 표시된다.
   통신 지연 시 이전의 즉시 낙관적 체크보다 느리게 느껴질 수 있다.
3. **동일 필드 동시 수정은 마지막 쓰기 우선이다.** 변경 컬럼만 보내 무관한 필드는 보존하지만,
   DB 버전/CAS가 없어 두 기기의 같은 필드 충돌까지 해결하지는 못한다.
4. **실패 요청은 현재 세션 메모리에만 있다.** 브라우저 종료/새로고침 후에는 재시도 큐·일반 폼 초안을 복원하지 않는다.
   서버가 실제로 저장했으나 응답이 유실된 경우에는 새로고침 후 저장된 행이 보일 수 있다.
   독립적인 두 기기에서 우연히 같은 문장을 새로 등록하는 동작까지 동일 작업으로 병합하지 않는다.
5. **복수 테이블 쓰기는 트랜잭션이 아니다.** 타이머의 시간 블록만 먼저 저장될 수 있다.
   같은 세션 재시도로 수렴시키며 이미 저장된 블록을 자동 삭제하지 않는다. 원자적 처리는 향후 별도 검토다.
6. **반복 TODO의 전체/이후 편집·삭제·날짜 이동의 복합 처리, 일반 삭제, 연간/분기 목표,
   태그·습관·회고 본문·일정 등은 기존 저장 패턴이 남아 있다.** 전체 DB 계층을 바꾸지 않았다.
   특히 기존 반복 항목 이동은 회차 취소와 새 TODO 생성이 별도 쓰기라 부분 실패 위험이 남는다.
   이번 단건 가상 회차 완료/편집은 확인 저장을 적용했지만 전체 반복 모델을 재설계하지 않았다.
7. **브레인스토밍 원본 삭제는 기존 메서드다.** TODO는 확인 후 생성되므로 실패 시 원본을 잃지 않지만,
   이후 원본 삭제 실패까지 하나의 트랜잭션으로 보장하지 않는다. 원본 기반 ID로 TODO 중복은 막는다.
8. 초기 전체 조회의 기존 오류 표시는 별도 개선 여지가 있다. 이번 핵심 Realtime/복귀 재조회에는
   실패 시 기존 값 유지 처리를 적용했다. 운영 마이그레이션 적용 상태나 RLS 차이는 확인하지 않았다.
9. STEP 1 보고서의 모호한 옛 ISO 키, 실행 날짜 없는 레거시 기록, 자정 통과 시간 분할 제약은 그대로 남는다.
   관련 소스의 계산 기준을 변경하지 않았고 기존 회귀 테스트는 통과한다.

## 7. STEP 3 권장 순서

1. 기존 `weeklyGoalId` / `monthlyGoalId`를 유지한 공통 화면용 조회 결과를 정의한다.
   주간 일정과 주간 플래너가 각각 TODO 복사본을 저장하지 않도록 한다.
2. 오늘 홈에 주간 목표와 공통 진행률, 날짜 미지정 TODO 진입점부터 배치한다.
   저장 중/실패/수동 기준/연결 TODO 기준을 작은 문구로 구별한다.
3. 퀘스트는 같은 TODO ID와 확인 저장 액션을 재사용한다. 취소·백로그와 수동 완료 규칙을 화면에 설명한다.
4. 빠른 기록은 기존 TODO/시간 블록에 연결된 최소 입력부터 제공한다.
   새 활동 테이블·독립 기록·연동은 데이터 설계를 확정한 뒤 별도로 다룬다.
5. 이번 범위 밖의 복합 이동/삭제 저장 처리와 격리 Supabase에서의 RLS·동시 수정·PWA 재접속 검증을
   작은 후속 작업으로 분리한다. 운영 데이터에서 시험하지 않는다.
6. 이후 동일 데이터로 월간 / 주간 일정·주간 플래너 / 일간을 구성한다.
   습관 체크·주간 회고도 기존 행을 참조하며 중복 저장 모델을 추가하지 않는다.
