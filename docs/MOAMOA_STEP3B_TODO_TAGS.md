## 2. 접근 경로와 실행 환경

실제 제품 연결 경로는 개발 서버의 **`/__moamoa-todos`**다. 기존 App → Auth → PlannerProvider를 사용하며, `import.meta.env.DEV` lazy route로만 등록했다. 기존 `/todos`, `/dashboard`, 캘린더 등 프로덕션 기본 경로는 그대로다. 새 오늘 홈의 할 일 진입점만 새 경로를 가리킨다.

실제 Supabase 설정이 있는 일반 개발 환경에서는 기존 로그인을 거쳐 접근한다. 이번 클라우드에서는 실제 Supabase/Auth/RLS를 이용한 종단 검증을 수행하지 않았다. 운영 DB로 대신 검증하거나 자격증명을 추가하지 않았다.

직접 눌러볼 수 있는 격리 시연은 다음과 같다.

```sh
TZ=Asia/Seoul MOA_REVIEW_PORT=5176 node scripts/test/serve-moa-today.mjs
# http://localhost:5176/__moamoa-todos
# http://localhost:5176/__moamoa-today
```

화면 상단에 `격리 시연 · 메모리 샘플 · 새로고침 시 초기화`가 표시된다. 실제 App/Auth/Provider/DB 변환 코드를 사용하되 전송만 테스트용 메모리로 바꾼다. 제품 코드에 샘플 fallback을 넣지 않았다. 시연의 데이터는 브라우저 페이지 메모리에 있고 새로고침 시 초기화된다. 시연 서버를 실제 저장·실제 여러 기기 동기화 확인 용도로 사용하면 안 된다.

## 4. TODO 관리와 버튼별 실제 동작

| 버튼/입력 | 구현·검증 결과 |
| --- | --- |
| + 할 일 추가 / 빠른 기록 | 같은 입력 시트를 연다. 모바일 바텀시트, PC 모달. 제목만 저장 가능 |
| 저장 | 기존 `addTodo`/`updateTodo` 확인 후 목록 반영·시트 닫기. 생성 ID는 초안 동안 고정 |
| 취소 / 닫기 | TODO 초안이 바뀌었으면 확인, 저장 중 닫기 방지. 바깥 클릭으로 초안을 잃지 않게 함 |
| 날짜 선택 | 날짜/종료일 입력 및 날짜 지정 해제. 날짜 미정 탭에서는 신규 날짜도 기본 미정 |
| 예정 시간 | HH:mm 입력. 기존 확장 시간도 표시·보존. 실제 사용 시간에는 합산하지 않음 |
| 구분 | 기존 `Todo.category`에 업무/work, 라이프/life, 개인 프로젝트/project 저장. 다른 기존 값은 자동 치환하지 않음 |
| 대표 카테고리 | 시간 추적 태그 최대 1개 또는 선택 안 함. 기존 다중 태그는 명시적 변경 전까지 보존 |
| + 태그 | 일반 태그 검색·다중 선택·해제·새 태그 생성·관리 진입 |
| 목표 연결 | 기존 주간 목표의 이름/주차/공통 진행률을 표시. 선택·변경·해제 가능 |
| 태그 관리 | 생성/편집/삭제가 실제 확인 저장에 연결. 읽기만으로 추천 태그를 저장하지 않음 |
| 수정 / 상세 보기 | 같은 TODO ID를 사용. 변경된 편집 필드만 전달해 상태·다른 연결 정보를 덮어쓰지 않음 |
| 완료 | `updateTodo`+기존 길이 0 완료 마커 정책. 해당 활성 타이머는 기존 finish 액션 사용. 실패 시 기존 상태 유지 |
| 삭제 | 확인 시트 → 서버의 최신 TODO/시간 블록 확인 → 삭제 → 서버에서 부재 확인. 응답 유실 재시도 가능 |
| 취소 상태로 보관 | 실적이 있는 TODO는 hard delete 대신 취소로 보관해 시간 블록을 유지. 목표 분모에서는 공통 규칙대로 제외 |
| 시간 기록 | 연결 TODO·날짜·소요·대표 태그를 표시하고 기존 블록 저장. 완료 상태는 변경하지 않음 |
| 목록·필터 | 오늘/이번 주/날짜 미정, 구분·검색·태그·목표·상태 조합. 기본은 진행·완료이며 취소/보관은 명시적 필터로 조회 |

주간 목록은 ISO 주차 및 레거시 키 읽기 호환을 재사용한다. 날짜 미정이면서 이번 주 목표에 연결된 TODO는 이번 주와 날짜 미정에서 같은 ID로 보인다. 목표 없는 날짜 미정 TODO를 임의로 특정 주에 배정하지 않는다.

시각적 체크박스는 25px이고 실제 버튼 영역은 44×44px이다. 긴 제목은 줄바꿈하며, 모바일 하단 메뉴·기록 버튼은 스크롤 콘텐츠 바깥 공간을 사용한다. 입력 시트는 본문 스크롤과 저장/재시도 영역을 분리한다. 중첩 시트도 배경을 가리고 focus를 유지한다.

## 5. 태그 선택과 관리

신규 TODO에서는 `trackTime=true` 태그 0~1개, 일반 보조 태그 여러 개를 고른다. 제목만 기록할 수 있도록 대표 선택도 선택 사항이다. 같은 `Todo.tags`에 ID를 저장하며 순서에 대표 의미를 숨기지 않는다. 보조 태그에는 시간을 배분하지 않는다.

기존 다중 시간 태그는 `기존 N개 · 균등 분할`로 표시하고 일반 편집/완료로 축소하지 않는다. 대표 선택을 바꾸는 명시적 동작에는 과거 재분류 영향 확인을 받는다. 알 수 없는 기존 ID도 자동 삭제하지 않는다.

추천 이름은 업무·자기계발·개인 프로젝트·운동·생활·휴식이다. 누르면 입력만 채우며 사용자가 저장할 때만 생성한다. 색상·이름·시간 카테고리/일반 용도를 관리할 수 있다. 사용 중인 태그는 삭제와 용도 변경을 차단하며 이름·색상 수정은 가능하다.

삭제/용도 변경 전 `todos`와 `events` 전체 RLS 가시 범위를 서버 필터로 확인한다. Provider가 읽은 일정 기간만 보고 미사용으로 판단하지 않는다. 실제 검증에는 Provider 범위 밖 2015년 일정의 태그도 포함했다. 과거 기록 보호를 위해 모든 TODO를 다시 upsert하거나 태그 참조를 자동 제거하지 않는다.

기존 동기식 `addTag`/`updateTag`/`deleteTag`의 계약은 바꾸지 않고, 새 화면은 `createTagConfirmed`/`editTagConfirmed`/`removeTagConfirmed`를 사용한다. 기존 DB codec·SaveCoordinator 패턴·Provider 상태를 재사용하므로 별도 태그 데이터 저장소는 없다.

## 6. 목표 연결·해제

목표는 선택 사항이며 태그와 독립적이다. 연결 없는 생활 TODO도 등록·완료할 수 있다. 목표 선택/해제는 `weeklyGoalId`만 바꾸며 주간→월간 연결은 유지한다.

회귀 fixture에서 주간 목표는 연결 전 1/3=33%, 미완료 TODO 연결 후 1/4=25%, 연결 TODO 완료 후 2/4=50%로 변했다. 일반 미연결 TODO 완료로는 변하지 않았다. 해제 후 원래 원본 TODO 기반 진행률로 돌아간다. 주간은 `weeklyRollup`, 월간은 `monthlyRollup`을 동일 원본으로 계산한다. XP 정책은 바꾸지 않았다.

## 7. 실제 시간 기록과 집계

- 기존 `todo_time_blocks`에 ID/TODO ID/실제 작업 날짜/`elapsedSec`만 저장한다. 소요만 입력했으면 `start_time`, `end_time`은 null이다.
- 15/30/60분 또는 1~1440분 직접 입력. 서버 확인 후 반영하며 안정적인 요청 UUID로 중복 클릭·응답 유실 재시도를 처리한다.
- 실제 90분 기록 시 대표 태그에 90분이 더해지고 완료 여부는 그대로다. 계획 시간과 체크만으로는 시간이 늘지 않는다.
- 모든 요약은 원본 TODO·Event·태그·블록으로 `aggregateActivity`를 호출한다. 실제 총시간, 분류 시간, 미분류 시간을 구분하고 계산 불가 기록은 건수로 표시한다. 새 통계 대시보드는 만들지 않았다.
- 태그 2개의 레거시 실제 60분은 각 30분으로 분할한다. 대표 태그를 해제해도 실제 총시간은 유지하고 미분류로 이동한다.
- 수면·운동 라이프 로그는 추가 입력 소스로 합산하지 않는다.

### 최초 수동 기록과 기존 do_* 실적 보존

기존 집계는 블록을 우선하므로 레거시 실적 60분이 있는 TODO에 새 15분 블록만 만들면 기존 60분이 합계에서 빠질 수 있다. 첫 수동 기록에서 서버의 현재 TODO와 해당 블록을 확인하고, 블록이 없다면 날짜·시각이 명확한 기존 실적을 별도 블록으로 함께 보존한다. 기존 do_*를 삭제하거나 바꾸지 않는다.

보존 블록 ID는 TODO ID로부터 결정적으로 계산하는 UUID여서 재시도/다른 기기의 동일 보존이 중복 행을 만들지 않는다. 보존이 먼저 성공하고 새 입력이 실패해도 기존 실적은 유지되며 같은 요청으로 명시적 재시도한다. 두 쓰기가 DB 트랜잭션인 것처럼 표시하지 않는다.

새 입력에는 가짜 시각을 만들지 않는다. 기존 60분(1월 1일) + 새 15분(1월 2일)은 각 일 60/15분, 해당 주 75분으로 검증했다. 레거시 날짜가 없거나 23:50→00:10처럼 의미가 불명확하면 임의 변환 대신 오류를 표시하고 기존 기록 확인을 요청한다.

기존 렌더 하네스는 PC timeblock 탭·일부 daily 메뉴/모바일 일정 편집/반복 팝업을 찾지 못해 스킵했다. 해당 레거시 팝업 전부를 검증했다고 주장하지 않는다. 신규 모아모아 시트는 별도 통합 테스트로 직접 열어 검증했다.

## 10. 데이터 모델 제약·미해결 사항·회귀 위험

1. `Tag.trackTime`은 전역 속성이다. 같은 태그를 TODO마다 대표/보조로 다르게 쓰는 모델은 없다. 새 UI는 시간 태그 0~1개 + 일반 태그 여러 개라는 최소 제약을 사용하며 새 DB 필드는 만들지 않았다.
2. 시간 블록은 현재 TODO 태그를 참조하므로 이후 태그 선택을 바꾸면 과거 시간도 재분류된다. 이름/색상 변경도 과거 표시를 바꾼다. 당시 분류 스냅샷은 없다.
3. 사용 여부 확인→삭제/용도 변경, 실적 확인→TODO 삭제 사이의 다른 기기 동시 쓰기를 DB 수준에서 원자적으로 막지는 못한다. 현재 스키마는 TODO 삭제 시 블록 cascade이며 태그 ID 배열에는 참조 FK가 없다. 이 경쟁 조건의 완전 차단에는 별도 서버/DB 변경 검토가 필요하다. 이번에는 선행 최신 조회·참조 차단·확인 저장을 적용하고 운영 DB는 변경하지 않았다.
4. 기존 레거시 화면의 동기식 태그/삭제 액션은 이전 동작을 유지한다. 새 화면의 확인 저장 보강이 모든 기존 화면을 전면 전환한 것은 아니다.
5. 반복 TODO는 새 항목에 매일/평일/매주 시작 설정만 제공한다. 반복 행의 편집·삭제·수동 시간 기록은 비활성화하고 제한 이유를 표시한다. 완료는 기존 회차 materialization을 재사용한다. 분기 삭제·기간 이동·완료 해제의 복잡한 정책은 확장하지 않았다.
6. TODO의 메모 저장 필드는 현재 모델/codec에 없다. 저장되는 척하지 않고 비활성화·후속 모델 안내를 표시한다.
7. 특정 주에만 배정된 날짜 미정 TODO의 전용 주차 필드는 없다. 연결 목표로 알 수 있는 주만 읽기 투영하며 별도 배정 데이터는 만들지 않았다. 습관은 별도 모델이다.
8. 현재 Provider의 일부 최초 조회가 오류를 빈 배열로 반환하는 기존 한계는 남는다. 새 태그/블록의 Realtime 조회 실패는 확인된 값을 지키지만 전체 초기 로드 오류 모델을 재작성하지 않았다.
9. 초안·재시도 요청은 현재 브라우저 메모리 범위다. 화면을 완전히 떠나거나 새로고침한 후 초안 복구·오프라인 영구 저장·자동 재시도는 없다.
10. 실제 Supabase/RLS·네트워크·복수 기기 종단 검증은 격리 환경이 준비되어야 한다. 이번 동기화 검증은 실제 Provider/구독 코드와 메모리 전송으로 수행했다.

## 11. STEP 3B-3 추천 범위

- 먼저 현재 TODO 연결 기록의 실사용을 확인하고, 일간·주간·월간 날짜/기간 선택을 동일 집계에 연결한다. 기존 요약·미분류·계산 불가 내역을 확장하며 별도의 계산식을 만들지 않는다.
- 독립 활동은 가짜 TODO를 만들지 않는 `activity_entries` 최소 모델을 별도로 설계한다. owner/안정 ID/실제 날짜·소요/대표 분류/선택적 메모를 검토하고 DB 변경은 승인 후 격리 환경에서 진행한다. 독립 활동을 TODO 블록과 이중 저장하지 않는다.
- 과거 분류를 고정하려면 기록 시점의 **태그 ID와 분배 비율을 가진 불변 분류 스냅샷** 또는 버전/유효기간 모델이 필요하다. TODO 블록과 독립 활동에 일관되게 적용하고, 레거시 스냅샷 없는 기록은 기존 균등 분할 fallback으로 읽는 정책을 정의한다. 이름/색상까지 당시대로 유지할지도 결정한다. 과거 분류를 현재 태그로 추정해 일괄 변환하지 않는다.
- 전역 태그 역할 대신 TODO별 대표 태그를 원하면 선택적 대표 ID와 레거시/대표 방식 구분까지 함께 검토한다. nullable 필드만으로 레거시와 대표 미선택을 혼동하지 않게 한다.
- 삭제 경쟁 조건의 서버 보호, 초기 읽기 오류 표시, 반복 회차별 시간 기록과 메모 모델은 작은 별도 승인/검증 단위로 다룬다. XP·주간 플래너·전체 DB 계층 개편으로 범위를 넓히지 않는다.
- 음식·문화·음악·독서는 기존 계획대로 독립 시간 기록 이후 STEP 3B-4에서 보존·개선한다.
